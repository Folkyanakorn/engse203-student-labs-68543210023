## 1. ภาพรวม

ระบบมี 2 ตาราง ความสัมพันธ์เป็น **หนึ่งต่อหลาย (one-to-many)** — ผู้ใช้ 1 คนแจ้งคำร้องได้หลายรายการ แต่คำร้อง 1 รายการเป็นของผู้แจ้งคนเดียว

```
┌───────────────────┐            ┌────────────────────────┐
│ users             │            │ requests               │
├───────────────────┤            ├────────────────────────┤
│ id  (PK, INTEGER) │ 1        ∞ │ id  (PK, TEXT)         │
│ name              │◄───────────│ requester_id (FK)      │
│ department        │            │ request_type           │
│ email (UNIQUE)    │            │ location · details     │
└───────────────────┘            │ priority · status      │
                                 │ created_at             │
                                 └────────────────────────┘
```

## 2. ทำไมต้องแยกเป็น 2 ตาราง

ช่วง Week 06–07 เราเก็บ `requesterName` เป็นข้อความซ้ำในทุกคำร้อง ซึ่งมีปัญหา 4 ข้อ

| ปัญหาของการเก็บชื่อซ้ำในทุกคำร้อง | การแยกตารางแก้อย่างไร |
|---|---|
| **ข้อมูลซ้ำ** — "สมชาย ใจดี" ถูกเก็บซ้ำทุกครั้งที่แจ้ง (ในข้อมูลชุดนี้สมชายแจ้ง 3 รายการ = ซ้ำ 3 ที่) | เก็บชื่อที่เดียวใน `users` คำร้องอ้างด้วย `requester_id` เท่านั้น |
| **แก้ไม่ครบ** — ถ้าสมชายเปลี่ยนชื่อ ต้องไล่แก้ทุกแถว ถ้าแก้พลาดบางแถวจะมีทั้งชื่อเก่าและชื่อใหม่ปนกัน | **ตอบคำถาม "สมชายเปลี่ยนชื่อต้องแก้กี่ที่" ได้ว่า 1 ที่** (`UPDATE users` แถวเดียว) ทุกคำร้องเห็นชื่อใหม่ทันทีผ่าน JOIN |
| **เก็บข้อมูลผู้ใช้เพิ่มไม่ได้** — จะเก็บภาควิชาหรืออีเมล ต้องซ้ำไปทุกคำร้อง และผู้ใช้ที่ยังไม่เคยแจ้งไม่มีที่อยู่ในระบบ | `users` มี department และ email ของตัวเอง และมีผู้ใช้ที่ยังไม่มีคำร้องได้ (เช่น วิชัย มั่นคง) |
| **พิมพ์ผิดแล้วไม่มีใครรู้** — "สมชาย ใจดี" กับ "สมชาย ใจดี " (เว้นวรรคท้าย) จะถูกมองเป็นคนละคน | ผู้ใช้ 1 คน = 1 แถว มี `id` เดียว และ Foreign Key ไม่ยอมให้ชี้ไปหาผู้ใช้ที่ไม่มีอยู่จริง |

## 3. รายละเอียดตาราง

### users

| คอลัมน์ | ชนิด | ข้อกำหนด | เหตุผลที่เลือกแบบนั้น |
|---|---|---|---|
| id | INTEGER | PRIMARY KEY AUTOINCREMENT | ให้ฐานข้อมูลรันเลขให้เอง ไม่ซ้ำ และเป็นตัวเลขจึงเทียบ/JOIN ได้เร็ว |
| name | TEXT | NOT NULL | ผู้ใช้ที่ไม่มีชื่อไม่มีความหมายกับระบบ |
| department | TEXT | NOT NULL | ใช้กรองคำร้องตามภาควิชา (query ข้อ ⑥) |
| email | TEXT | NOT NULL UNIQUE | ใช้ระบุตัวตนจริงของคน ชื่อซ้ำกันได้ แต่อีเมลซ้ำไม่ได้ |

### requests

| คอลัมน์ | ชนิด | ข้อกำหนด | เหตุผลที่เลือกแบบนั้น |
|---|---|---|---|
| id | TEXT | PRIMARY KEY | ใช้รหัสอ่านง่ายแบบ `REQ-001` ที่ผู้ใช้เห็นและพูดถึงได้ |
| requester_id | INTEGER | NOT NULL · FOREIGN KEY → users(id) | ทุกคำร้องต้องมีเจ้าของ และเจ้าของต้องมีอยู่จริง |
| request_type | TEXT | NOT NULL · CHECK 4 ค่า | จำกัดประเภทให้ตรงกับที่ระบบรองรับ กันค่าแปลกปลอม |
| location | TEXT | NOT NULL | ช่างต้องรู้ว่าไปที่ไหน |
| details | TEXT | NOT NULL | คำร้องที่ไม่มีรายละเอียดทำงานต่อไม่ได้ |
| priority | TEXT | NOT NULL DEFAULT 'normal' · CHECK (normal, urgent) | ถ้าไม่ระบุถือว่าปกติ และรับได้แค่ 2 ค่า |
| status | TEXT | NOT NULL DEFAULT 'pending' · CHECK (pending, in-progress, completed) | คำร้องใหม่เริ่มที่รอดำเนินการเสมอ |
| created_at | TEXT | NOT NULL DEFAULT เวลาปัจจุบัน | ให้ฐานข้อมูลบันทึกเวลาเอง ไม่ต้องพึ่งโปรแกรมส่งมา ใช้หา "ล่าสุด" ได้ |

นอกจากนี้มี `INDEX idx_requests_status` บน `requests(status)` เพื่อให้ค้นตามสถานะเร็วขึ้นเมื่อข้อมูลมาก

## 4. เหตุผลของการเลือกชนิดและข้อกำหนด

**ทำไม `users.id` เป็น INTEGER แต่ `requests.id` เป็น TEXT**
`users.id` เป็นเลขภายในที่ผู้ใช้ไม่เคยเห็น จึงให้ฐานข้อมูลรันเลขอัตโนมัติ (AUTOINCREMENT) ส่วน `requests.id` เป็นรหัสที่คนใช้อ้างอิงและพูดคุยกัน (`REQ-001`) จึงต้องอ่านง่ายและมีรูปแบบ ซึ่งเป็นข้อความ ถึงฐานข้อมูลจะสร้างเลขให้เองไม่ได้ แต่แลกกับการที่ผู้ใช้จำและพูดถึงรหัสได้

**ทำไมต้องมี CHECK constraint ทั้งที่ API ก็ตรวจข้อมูลอยู่แล้ว**
เพราะ API ไม่ใช่ทางเดียวที่แก้ข้อมูลได้ — ยังมี script, การแก้ผ่านเครื่องมือฐานข้อมูล หรือ API เวอร์ชันอื่นที่อาจลืมตรวจ CHECK เป็นด่านสุดท้ายที่ทำให้ข้อมูลผิดเข้าฐานข้อมูลไม่ได้ไม่ว่าจะมาจากทางไหน ถ้าจะแก้กฎก็แก้ที่เดียว (หลักการ "defense in depth" คือป้องกันหลายชั้น ไม่พึ่งชั้นเดียว)

## 5. ตัวอย่างการใช้ JOIN

```sql
SELECT r.id, u.name AS requester, r.request_type, r.status
FROM requests r
JOIN users u ON u.id = r.requester_id
ORDER BY r.id
LIMIT 4;
```

| id | requester | request_type | status |
|---|---|---|---|
| REQ-001 | สมชาย ใจดี | แจ้งซ่อม | pending |
| REQ-002 | สุภาวดี รักเรียน | บริการบัญชีผู้ใช้ | in-progress |
| REQ-003 | ธนกฤต ตั้งใจ | ขอใช้อุปกรณ์ | completed |
| REQ-004 | สมชาย ใจดี | แจ้งซ่อม | pending |

## 6. ข้อสังเกตสำหรับสัปดาห์ที่ 10

ผลของ JOIN มีหน้าตาเกือบเหมือนข้อมูลที่ API ส่งให้ React ใน Week 07 (`{ "id": "REQ-001", "requesterName": "สมชาย ใจดี", "status": "pending" }`) ต่างกันที่ฐานข้อมูลเก็บ `requester_id` เป็นตัวเลข แต่ผู้ใช้เห็นเป็นชื่อ

ข้อสรุปของผมคือ **ชั้น service ต้องแปลงข้อมูลสองทาง**: ตอนอ่านใช้ JOIN พร้อมตั้งชื่อคอลัมน์ใหม่ (`u.name AS requesterName`) ให้ได้รูปแบบเดิมที่ frontend คาดหวัง ส่วนตอนสร้างคำร้อง frontend ส่งชื่อมา service ต้องหา `id` ของชื่อนั้นก่อน (หรือสร้างผู้ใช้ใหม่ถ้ายังไม่มี) แล้วจึง INSERT ด้วย `requester_id` เพราะ Foreign Key จะปฏิเสธชื่อที่ไม่มี id รองรับ ดังนั้น frontend และ controller ไม่ต้องรู้เลยว่าข้างหลังเปลี่ยนเป็นสองตาราง
